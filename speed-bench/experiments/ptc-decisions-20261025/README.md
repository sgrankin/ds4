# Programmatic decisions: fixed synthetic screen

The fixture source is [fixtures.nu](fixtures.nu). It generates ordinary and
favorable queues plus an external oracle under the chosen ignored output path.
No gold label is sent to either model. [RESULTS.md](RESULTS.md) records the
measured screen, retained failures and current limits; generating the fixture
alone is not model validation.

The task asks for active account-takeover ticket IDs, their count, the largest
reported charge and a short handoff. Six of the 24 long records qualify. Decoys
include resolved incidents, simulations, hypothetical concerns, mistaken alerts
and ordinary billing/software cases; some excluded records have larger charges.
The four-record ordinary queue has two positives and short notes.

The model can use one bound choice template to construct one question per
record, make one native helper request against the whole queue, then filter,
join and compute the maximum in JavaScript. Only that compact result needs to
reach the generator. Full intermediate probabilities remain in the audit.

## Run

Start one generator plus Clef-Flash under the existing pressure guard. Configure
durable Responses storage for the qualification/restart cases. The runtime and
host tests are separate; these drivers never launch or stop a model.

```nu
# First prove execution, native callback parity and transports with explicit code.
nu tests/programmatic-decisions.nu --suite qualify
# Then measure natural task prompts, without naming a tool or supplying code.
nu tests/programmatic-decisions.nu --suite scenarios --repeats 2
# A quick first screen can use --repeats 1 or --case ordinary.
# Restart the same server with the same store, then:
nu tests/programmatic-decisions.nu --suite restart
```

`--model`, `--helper`, `--url`, `--python` and `--output` override their defaults.
The Python environment needs the same SDK/WebSocket packages as
`tests/hosted-decisions.nu`. Requests, responses and result tables stay local.

## Comparisons and interpretation

Three arms share the same natural user task and generic tool-use policy:
main-only, direct hosted decision helper, and programmatic helper composition.
The ordinary case exposes full evidence in every arm, so it can measure voluntary
tool use and unnecessary overhead. A correct direct answer without a tool is a
valid outcome there.

In the favorable case, main-only receives the full queue; helper/code arms
receive the policy and ID/charge manifest while notes stay in bound data.
This measures the benefit of data placement. It does not establish spontaneous
delegation with equal visible context, because accessing hidden notes requires
the supplied tool capability.
The PTC arm combines bound schemas, code execution and intermediate-result
filtering. A speed difference is for that package, not an isolated JS-engine
effect; direct hosted questions are still generated by the main model.

Start with helper prefix caching disabled for a simple matched comparison.
Record cache settings and actual main cached-token counts. If repeated-state
caching is studied later, compare both helper arms at the same warmness.
The initial screen needs only six configurations and two repetitions; alternate
arm order on the second repetition. Stop after a useful measurement is possible.

Record wall time, main input/output/cached tokens, outer program count, native
helper count/time, request/response bytes and compact program-result bytes.
Task checks compare IDs/count/maximum against the independent oracle; retain
JSON-format defects and raw handoff text for review. Scenario `pass` means the
requests completed without protocol errors; `correct` reports task quality
separately. Read the handoff for invented actions or claims unsupported by the
evidence rather than treating parseable JSON as sufficient quality.

Existing source hooks are enough for attribution: `DS4_CLEF_TIMING=1` prints
queue/prepare/backbone/head milliseconds and actual `clef-cache` reuse counts;
ordinary helper `usage.cached_tokens` currently reports zero. Main Responses
usage already includes tool-result continuation input and cumulative generation.
Do not enable the synchronized `DS4_CLEF_PROFILE` diagnostic for final wall time.

Keep the full experiment within one hour after runtime qualification: roughly
ten minutes for fixture/launch settings, twenty for the six-arm screen, twenty
for a useful repeat or a DeepSeek favorable pair, and ten for inspection/report.
If the model ignores tools, emits broken code or misclassifies the decoys, keep
that result and report which part failed; do not turn the hour into prompt tuning.
