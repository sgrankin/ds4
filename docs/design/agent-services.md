# Candidate agent services

This page preserves a design discussion from 23 October 2026, not an implementation plan. Memory, thread tools, agent jobs and compaction described here are not implemented or selected as a package. No database, indexing scheme or universal tool framework has been chosen. The later decision removed the generic server-hosted orchestrator; the agent owns ordinary tool composition and workflow state. The [hosted orchestration account](../lab/journal/2026-10-26-hosted-orchestration-lessons.md) explains that decision. Focused operations over server-owned context may still be worth considering independently.

## Memory, threads and working context

Cross-session memory would store checkable facts, decisions, constraints and evidence references beyond a single active prompt. It is distinct from response ancestry, inference caches and a compacted working context. A useful first contract might let a caller put, read, update and retract scoped text notes, retaining source thread and item identifiers and identifying superseded conclusions. Automatic promotion and indexing remain open choices.

Thread listing and opening could expose bounded outlines or selected messages. Search could return small snippets and stable references across notes, archives and thread history, with a separate exact read. Archiving a thread should retain searchable history; it is neither deletion nor removal of turns from the active working view. Context inspection could show the token budget, a bounded turn index and large contributors. An edit could archive selected turns before replacing or removing them from the working view, apply at a safe inference boundary and return a receipt and token usage. Edits should target a known thread revision so a stale concurrent edit fails visibly.

A concrete qualification would finish an investigation, archive detailed turns, save its conclusion and evidence references, and leave a pointer in context. A fresh session should then find the rejected kernel variant and retrieve its measurement and command. The archive must exist before the only copy is removed. Later possibilities include forking from a selected turn, asking a bounded question against another thread with cited evidence, and restoring a prior logical context revision. A cross-thread question spends inference; it is not merely search. Restoring logical context also does not promise exact restoration of an approximate inference state.

## Bounded agent jobs

The user also described an agent as a server-hosted tool: a parent asks a child to pursue a bounded goal with its own context, tool scope and budget, and receives a concise result and evidence references while the trace remains separately inspectable. Awaiting a child and detaching it with a durable handle are possible lifetime policies, not implemented behavior. A detached task could be inspected, cancelled or supplied requested input. It needs enough durable state to meet its stated recovery promise, and must record completed actions so restart does not blindly repeat external effects. A returned ID alone does not make a job restart-safe. An awaited child may instead follow parent cancellation; current response disconnect behavior is not that job contract. Logical jobs sharing a scheduler do not imply concurrent GPU execution or a speedup.

If pursued, an adapter could expose one job owner through more than one protocol rather than creating separate schedulers. An MCP adapter is an interoperability possibility, not the agent runtime. The 23 October 2026 protocol research found experimental Tasks in [MCP 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/tasks), followed by the [2026-07-28 revision](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/changelog.mdx) and its [Tasks extension](https://modelcontextprotocol.github.io/ext-tasks/specification/2026-07-28/tasks.html), which specifies `tasks/get`, `tasks/update` and `tasks/cancel`. This is dated protocol research, not evidence of ds4 support; verify the applicable pinned version before designing an adapter. It does not select outbound MCP hosting or reinstate the removed executor.

## Background compaction and recovery

Idle work could prepare a private candidate summary of a completed response's older prefix without changing the response or live context. When new input arrives, foreground work takes priority. A finished candidate is eligible only if its source prefix and model, prompt and configuration checks still match and the request permits compaction. Otherwise the server uses the ordinary context without waiting for speculative work.

If adopted at the start of the next response, the actual working view must combine the compacted prefix, exact retained tail and fresh user and tool input. A replayable checkpoint covering that complete frontier must precede new assistant output; each branch needs a checkpoint for its actual adopted view. A summary prepared before the new user input is insufficient if a client discards everything preceding the checkpoint. Preserve the previous recovery path until the replacement is durable or delivered as required by the persistence mode. Preparation must not append events to the already completed response.

This is a proposed scheduling policy, not an unsolicited protocol event. OpenAI's [compaction documentation](https://developers.openai.com/api/docs/guides/compaction) describes output during a response; its [background responses](https://developers.openai.com/api/docs/guides/background) concern asynchronous execution of a requested response, not general idle maintenance. The locally pinned OpenResponses 2026-04-24 core was reviewed for the original discussion and does not define unsolicited idle compaction output. The server has not implemented this proposed flow.

A self-contained opaque checkpoint plus retained window could allow client replay without durable per-session server history, provided its decoder and any keys survive. A reference into volatile server memory is not self-contained and does not imply provider portability. If the client retains only response IDs and deltas without sufficient replay state, restart recovery requires durable server storage of the effective context and referenced data. Replaying original history and recompacting is a fallback, but may produce a different working context. Logical history and optional inference snapshots have different roles: ordinary KV can be rebuilt from effective tokens, whereas an approximate suffix graft may require its snapshot to restore that particular state. A disconnect before checkpoint delivery must not erase the only recoverable copy.

Any experiment should start with one candidate per thread and measure foreground delay, adoption rate, saved compaction and prefill time, wasted background work and practical retrieval quality. Foreground priority requires bounded GPU work and yield or cancellation points, not just host-thread priority. Account for session switching, memory pressure and persistence policy; idle compute and shorter prompts are not automatically free. Memory extraction can be a separate task that does not rewrite active context.
