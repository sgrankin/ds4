# DeepSeek semantic checkpoints for edited context

## Context

The selected server `persistent-fast` package keeps anchor checkpoints and collects them during ordinary prefill. A semantic endpoint is a saved inference frontier at an eligible message or tool boundary; it can make a later unchanged part of an edited conversation available for reuse. On the tested two-edit workloads, the first implementation made edits faster but made initial population expensive; anchor selection and in-sweep capture reduced that setup cost. A later fresh-request comparison found no clear checkpoint overhead. These are separate comparisons, not one cumulative speedup.

This matters when a client shortens tool output while preserving subsequent investigation. Imagine a request containing a large file dump A, investigation C, and an old tool result D. The client replaces A with an excerpt and changes D. A checkpoint that actually ends after C allows the server to evaluate the shortened prefix, import C, and evaluate the new D. A final checkpoint after D cannot simply be truncated to C: its rolling attention windows, compression carries and other frontier state have already advanced. The [suffix matcher](../../../src/suffix_match.zig) matches token IDs through a saved endpoint, requires at least 64 reusable tokens and currently imports one span. It is not a general message diff.

The client owns the conversation archive and materializes the edited working view. A checkpoint is disposable inference state, not that archive. The [design discussion](../../CONTEXT_COMPACTION_AND_CHECKPOINTS.md) gives the motivating compaction example; the [recipe](../../../recipes/16-semantic-context-checkpoints.md) describes the implemented mechanism and configuration.

## Setup

The experiments ran on an M5 Max with 128 GiB RAM, using DeepSeek V4.1 Flash 1017 IQ2_XXS/Q2_K, high reasoning, native expert routes, packed main and index KV, and no MTP. The repeated-edit comparisons used ordinary serial and favorable parallel tool layouts, 24 fixture rows, initial population and two edits. Five fresh processes per arm ran in alternating order. Ordinary and favorable are separate workflows; each combined result sums their times within a round, so it has five paired samples. HTTP time includes prefill and generation, excludes process startup, and the second case shares warm model weights. Context keys were distinct and cold; the OS file cache was not flushed.

The benchmark used a 32 GB expert budget, a configured 8,192-token prefill chunk with a 2,048-token coordinator quantum, and 512 MiB hot / 4,096 MiB SSD cache budgets. This is not the wrapper's default configuration: server `persistent-fast` retains its 64 GB expert target and 512-token default chunk. Explicit overrides remain available. Detailed commands, settings and all samples are linked below. The original rows=72/eight-edit calibration was stopped because the full run exceeded the budget; the completed rows=24/two-edit cohort is separate, not a mixture of the two.

## Findings

The initial implementation captured complete frontiers at semantic message and tool boundaries, with bounded hot retention. It stopped model execution at selected ends. Those extra short segments repeatedly streamed model weights; capture and publication alone did not explain the setup cost. At frozen revision `d5b8e8a3`, the [off/sparse1/fuller4 comparison](../../../speed-bench/experiments/context-boundaries-20261028/RESULTS.md) produced the following combined times in seconds, mean ± sample standard deviation:

| Policy | Initial | Two edits | Whole |
| --- | ---: | ---: | ---: |
| Off | 80.005 ± 0.924 | 158.755 ± 2.870 | 238.761 ± 2.357 |
| Sparse1 | 100.847 ± 0.354 | 158.272 ± 3.002 | 259.119 ± 3.052 |
| Fuller4 | 145.486 ± 2.692 | 98.390 ± 2.940 | 243.876 ± 5.592 |

Fuller4 improved the two edits in all five rounds, but its whole time at this horizon was slower in four and faster in one. Sparse1 retained a later source but lacked early exact-prefix anchors and did not materially improve edit time. All 90 answers passed. The off arm still had ordinary cache behavior; it was not a no-cache baseline. The report includes individual cases, all samples, storage and order effects.

A separate [selection comparison](../../../speed-bench/experiments/context-capture-20261028/SELECTION.md), at `6b7cec74`, kept semantic capture enabled and changed which endpoints were selected: from recent endpoints to the first and last anchors in the same bounded recent-selection set. Combined initial time fell from 145.546 ± 3.833 to 128.069 ± 2.346 seconds, and whole time from 244.052 ± 5.648 to 225.086 ± 2.595 seconds. On the ordinary layout, the change eliminated a full-weight sweep; the favorable layout exposed a scheduler split and showed a smaller mixed change. Prefix and suffix reuse remained available, and 60/60 answers passed.

The next [collector comparison](../../../speed-bench/experiments/context-capture-20261028/COLLECTION.md), at `28c98fd7`, held anchors fixed and compared segmented capture with capture inside the existing layer-major sweep. Combined initial time fell from 127.839 ± 1.681 to 81.437 ± 2.046 seconds; two edits were 96.661 ± 0.970 versus 96.914 ± 0.533 seconds; whole time fell from 224.500 ± 1.865 to 178.352 ± 2.269 seconds. All five whole-time pairs improved and 60/60 answers passed. Profiling was enabled on both sides: large layer sweeps fell from 11 to 8. Logical PREAD volume fell, but that is not a measurement of physical SSD traffic. Peak logical hot pages increased from 231.794 to 270.226 MiB and SSD pages/manifests from 182.168 to 220.652 MiB. The hot-page figures stayed below the configured hot budget in this cohort.

The key change is collecting an endpoint's rolling state before later tokens overwrite it, while leaving the live forward at its final frontier. Snapshot serialization and hashing still cost work. The [Apple Silicon implementation](../../models/deepseek/apple-silicon.md#checkpoints-edits-and-speculation) explains the current state handling and fallback.

The latest [no-edit comparison](../../../speed-bench/experiments/context-capture-20261028/NO_EDITS.md), frozen at `f74180e0`, compared semantic checkpoints off with anchors and in-sweep capture on. Each case was one fresh HTTP request, with zero cached input tokens, not a long append-only session. Ordinary request time was 39.717 ± 1.358 seconds off and 38.908 ± 0.371 on; favorable was 41.586 ± 0.846 off and 41.871 ± 0.712 on. Paired changes varied in direction, so this establishes no clear speedup or penalty. All 20 answers passed. Ordinary caching and RAM/SSD tiers remained enabled in both arms; startup was recorded separately.

Correctness has several distinct meanings. The [native qualification](../../../speed-bench/experiments/context-capture-20261028/QUALIFICATION.md) found the final forward's full logits byte-identical with and without collection, and restored and recaptured endpoint snapshots exactly. Separately stopped endpoint teachers used different batch shapes and showed small nonzero differences: across 18 teacher rows, mean delta-NLL was −0.002516 nats/token and mean KL was 0.000559 nats, with maximum KL 0.005389. Those comparisons do not measure the quality of an edited history. A suffix graft is itself approximate: even with immutable pre-RoPE originals preventing accumulated rotation error, saved activations retain influence from the old prefix.

Practical checks of changed and deleted facts and user controls passed 10/10 initial and edited replies. A separate check retrieved an original archived dump as a fresh tool result. The ongoing-task policy identifies compatible sources using actual system, developer and user messages in their original order, along with reasoning controls, tool declarations and response schema. Changing these controls invalidates that identity. A restart lost the RAM-only source and correctly recomputed the edited answer. A separate eight-edit retention check passed 18/18 replies and reused the original source through all 16 edits; it is a functional observation, not a comparative eight-edit timing. See the [first-slice qualification](../../../speed-bench/experiments/context-boundaries-20261028/README.md) and [collector qualification](../../../speed-bench/experiments/context-capture-20261028/QUALIFICATION.md) for cases and limits.

## Conclusion

The chosen server `persistent-fast` configuration enables semantic boundaries, ongoing-task reuse, anchor selection and in-sweep collection with a bounded 512 MiB hot tier. Ordinary runtime defaults, the direct agent and other presets do not acquire these new boundary defaults. Intermediate RAM-only endpoints can be evicted or lost on restart; missing or ineligible sources fall back to recomputation. Collection has model and mode restrictions, and suffix reuse excludes combinations including MTP, steering, tensor parallelism and decoder replay. The [recipe](../../../recipes/16-semantic-context-checkpoints.md) specifies those boundaries and the older capture fallback.

These results support the selected implementation for the measured DeepSeek workloads, not a universal speedup or guaranteed retention under pressure. Longer append-only sessions, broader real agent tasks and comparative long-edit performance remain unmeasured. The server does not perform compaction or maintain the client's factual archive.
