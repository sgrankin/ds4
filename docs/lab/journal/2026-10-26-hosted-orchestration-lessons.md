# Hosted orchestration lessons, 25–26 October 2026

The server-hosted tool experiments established execution and replay, but did not establish a reliable general advantage over client orchestration. The generic hosted orchestrator was subsequently removed: the agent owns tool composition and workflow state, while ds4 retains native inference, decision APIs, scheduling and serving state. These small historical screens mostly used two repeats per arm, below the current five-sample comparison standard.

## Context and setup

The hypothesis was that a generator could delegate classification to a co-resident decision model, filter records in a server-run program and return only a compact result to its own context. Initial Responses hosted decisions bound a loaded helper to a request and recorded results for replay. The subsequent programmatic tool calling (PTC) slice used bounded QuickJS programs, bound inputs and schemas, and explicit helper calls; replay retained receipts instead of executing calls again. Client-owned function tools remained client-executed. The [hosted decision report](../../../speed-bench/experiments/hosted-decisions-20261025/RESULTS.md) and [PTC report](../../../speed-bench/experiments/ptc-decisions-20261025/RESULTS.md) describe the historical implementation and tests, not current activation instructions.

A fixed synthetic queue task compared direct answers with code that classified and reduced records. The Flint/Clef-Flash screen gave ordinary medians of 5.48 seconds direct and 12.04 seconds with code; the favorable bulk case was 17.85 versus 13.78 seconds. Fields were correct, but Flint duplicated JSON in the favorable final text. The helper's six positives and eighteen negatives matched the oracle. Correct execution and useful natural tool choice were separate questions.

## Native reasoning and planning results

A DeepSeek control explicitly disabled reasoning on frozen runtime `4cf6eacf`: direct runs took 53.277 and 58.188 seconds, code 78.263 and 77.923 seconds. Median code time was 40.1% longer, with two program rounds; a direct handoff also overstated refund status. This is a control for that mode, not normal serving qualification. With native reasoning enabled, the same favorable comparison took 127.380 and 128.344 seconds direct versus 86.060 and 86.673 seconds with code, a 32.45% median reduction. Generated tokens fell from 1,078 to 641, including reasoning tokens from 948 to 392; all four answers had correct numeric fields, clean JSON and grounded handoffs. The helper classified all 24 records correctly. One task and two repeats do not establish a general gain, and the enabled and disabled modes are different comparisons, not interchangeable controls. [Full measurements](../../../speed-bench/experiments/ptc-decisions-20261025/RESULTS.md).

A server-side MCP bridge then qualified live discovery and calls, including anonymous Exa, separate from the fixed timing screen. The bridge imported selected schemas, retained receipts and did not rerun calls on replay; each import or invocation used a fresh remote session, so stateful browser workflows were not qualified. In the normal-reasoning fixed screen, ordinary medians were 39.79 seconds for preprovided evidence, 92.24 for direct MCP and 69.69 with code available. Favorable medians were 57.93, 59.21 and 105.71 seconds. Code fetched twice and emitted 10,887 bytes of bulk data and probabilities. All twelve numeric answers and JSON were correct, though the report retains a handoff caveat. Live Exa demonstrated integration, not a matched speed comparison. [MCP results](../../../speed-bench/experiments/mcp-tools-20261025/RESULTS.md).

The A/B/C follow-up tested clearer contracts, a small question-construction helper and immutable response-local JSON references. Explicit reference tests established restart, replay, isolation and rollback; natural requests did not use stash/load, so timing changes cannot be credited to reuse. The unfamiliar contract case overwrote target instructions and produced five false positives before the main model recovered from the records. See [planning results](../../../speed-bench/experiments/planning-abc-20261026/RESULTS.md).

Reference-oriented output limited inline emissions at 512 or 2,048 bytes. Both limits failed both tool-heavy tasks under eight shared calls, despite exact loads and fewer emitted bytes. With a hint and twelve-call allowance, two favorable runs succeeded in 159.16 and 141.26 seconds, compared with about 108 seconds for the disabled control; the unfamiliar case still failed twice. Generated projections could lose evidence without corrupting the stored reference. The later output-first instruction also failed both favorable attempts; a factual API clarification produced correct answers but mixed ordinary/favorable/unfamiliar median changes of +12.2%, -10.0% and +93.8%. Neither naturally used references. These are context, latency and quality tradeoffs, not established speedups. [Reference results](../../../speed-bench/experiments/reference-output-20261026/RESULTS.md); [output-first results](../../../speed-bench/experiments/output-first-20261026/RESULTS.md).

## Conclusion

The favorable reasoning-enabled result supports classification and reduction before handing bulk evidence to the generator. It does not isolate server execution from equivalent client-side composition. The later screens exposed extra generation, refetches, lost evidence and output volume as costs; functional persistence was not evidence that the model would use it effectively. After reassessment, generic hosted execution, MCP hosting and program-value persistence were removed in favor of client ownership. Normal client-executed Responses function calls and native decision operations remain distinct. Future server-owned context and recovery operations are considered in [agent services design](../../design/agent-services.md), without reinstating a generic executor.
