# DeepSeek on DS4 and DeepInfer

DS4 follows the DeepSeek V4.1 Flash model contract while adapting its execution to one Apple GPU and local storage. DeepInfer is a useful reference for the model's state, dataflow and serving techniques, but its released engine targets SM100 and Ascend950 systems, and its documented production service includes components outside the public release. This comparison distinguishes those sources from the native DS4 implementation. It is a guide to the differences, not a claim of identical kernels, numerics or performance.

The source audit uses DeepInfer [`553741557a57df44a46fb3ab72b6aafeaf945337`](https://github.com/deepseek-ai/DeepInfer/tree/553741557a57df44a46fb3ab72b6aafeaf945337) and deepseek-recipe [`935817c66f5d6e64838f419692545f06787e485f`](https://github.com/deepseek-ai/deepseek-recipe/tree/935817c66f5d6e64838f419692545f06787e485f). DS4's original audit baseline was `e2a38f6e2bf4`; subsequent local work and measurements are identified in their linked reports. The locally measured trunk is the 1017 IQ2_XXS/Q2_K quant, not the upstream native MXFP4 expert checkpoint. Consequently an upstream result is not a benchmark of this Mac or this quant.

For the model itself, start with the [reference manual](../reference-manual.md); for the native request and state path, see the [implementation manual](../implementation.md). The [Apple Silicon guide](../apple-silicon.md) explains the memory and Metal tradeoffs. The older [alignment inventory](../../../DEEPINFER_ALIGNMENT.md) provides source-level coverage of individual techniques.

## The shared model contract

Consider a long-context query at layer 20. Its indexer scores eligible
compressed index keys and selects up to 2,048 blocks of eight rows. Later
refreshes select rows within those candidate blocks; final attention uses the
selected main KV alongside the recent window. Candidate scores and selection
IDs are not attention weights or KV data. Both implementations preserve this
hierarchy in the validated profile, where layers 2, 8, 14 and 20 publish
compressed KV and index keys, and selection refreshes at 2, 8, 14, 20, 24,
28, 32 and 36. DeepInfer derives sharing relationships from checkpoint metadata;
DS4 implements the validated Flash topology. See [sharing and candidate
selection](../reference-manual.md#sharing-and-candidate-selection) and DeepInfer's
[cross-layer implementation](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/model_executor/models/v4_modules/cross_layer.py).

This ownership matters when restoring or shortening work. A complete continuation needs correctly positioned raw history, shared compressed and index blocks, pending compressor state and other model state. Saving text or a single attention array alone does not reconstruct those relationships. DS4 also stores durable conversation ancestry separately from disposable inference checkpoints: an SSD hit accelerates continuation but is not the conversation's source of truth. See [continuation and storage](../implementation.md#continuation-and-storage) and the [state-cache recipe](../../../../recipes/03-state-cache.md).

## Three windows, three jobs

Consider a long prompt restored from a retained compressed prefix, then prefilling
the remaining prompt and generating with a drafter. Each stage may retain or
discard different state, so its window solves a different problem.

An **encoder recovery look-back** reconstructs recent attention state after retaining a compressed prefix but discarding its raw sliding-window state. DeepInfer's deployment description gives a 128-token replay: if the retained prefix ends at position 32,768, replay starts at 32,640, with the replay floor restricting which raw keys are visible. The public engine contains that floor metadata; the complete production cache-hit controller is not released. See the [deployment description](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/doc/inference_deployment_qa.md) and [input preparation](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/csrc/engine/input_metadata/prepare_tensor_input_v4.cpp).

DS4 has an SWB1 diagnostic importer that preserves immutable blocks and reconstructs all 40 raw rings with 128 scalar replay rows. It demonstrates bounded recovery, but it is not an isolated encoder-only recovery policy, and ordinary SSD admission still requires complete checkpoint state. Full-state hits remain the faster established path. Batching the replay and deciding when a block-only hit is worth retaining are open choices, not enabled cache behavior. The [experiment report](../../../../speed-bench/experiments/deepinfer-alignment-20261027/README.md) describes the measured size and latency tradeoff.

A **decoder retained tail** serves a different purpose: reducing query work during prefill while still publishing the full encoder/global compressed history. DeepInfer can physically compact away decoder queries, including with DFlash, when configured; its truncation defaults off. Its retained tail must cover the 128-token attention window plus speculative backtracking: with five drafts, 134 is the minimum and 140 is an example, not a universal window. For eligible wide sweeps of at least 8,192 new rows, DS4 computes an exact
shrinking dependency suffix: as prefill advances
through decoder layers, it retains the query rows needed to produce the final
rows and their causal dependencies, shrinking that set where earlier rows can no
longer affect the result. Its optional fixed 128/256-row replay is an additional approximation restricted to sweeps of at least 8,192 rows, without DSpark or images; ordinary 512/2,048-row chunks do not activate it. Extending compaction to ordinary chunks is a proposal, not an authorized or completed experiment. See [DeepInfer's YOCO example](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/examples/yoco/README.md) and [local replay](../../../../recipes/12-bounded-decoder-replay.md).

A **drafter history window** supplies features needed to propose future tokens. DeepInfer's DFlash projects target features into drafter attention KV during forward; DS4's DSP1 checkpoint instead stores the exact raw BF16 target features and rebuilds projected drafter KV on use. This is neither encoder replay nor decoder query compaction. With DSP1, a restored session can draft immediately rather than waiting for new target features. In a separate five-pair, ordinary-confidence 0.6 campaign, complete restored time across three checked tasks fell 18.12% with matching outputs; stored files grew 10.343 MiB across three endpoints. This is a restore-workload result, not a general decode speedup. DSP1 export is enabled in opt-in DeepSeek fast presets and can be explicitly disabled; ordinary engine defaults remain unchanged. See [draft proposals](../implementation.md#draft-proposals-and-verification) and the [campaign](../../../../speed-bench/experiments/draft-features-five-20261028/README.md).

## Physical history and selection

Quantizing a value and expanding it back to floating point is different from keeping a packed allocation. DeepInfer stores raw sliding-window rows as FP8 plus scales, compressed main rows as FP4 plus scales, and index rows as FP4 plus scales. DS4's current raw GPU rows remain expanded F32: 2,048 bytes for 512 values, versus 528 bytes in the upstream packed format. Its fast presets physically pack main rows to 288 bytes and index rows to 68 bytes; their F32 counterparts occupy 2,048 and 512 bytes respectively. DS4 retains publication scales and supports the packed formats through scalar and batch readers and checkpoint conversion. The [main-KV recipe](../../../../recipes/15-packed-main-kv.md) explains formats and compatibility; [representing history](../apple-silicon.md#representing-the-history) explains their use on Metal.

The capacity gain is concrete, but it does not guarantee lower latency. In the index comparison, five alternating 32K pairs were roughly speed-neutral and showed exact observed teacher and output IDs; order effects prevent a reliable speedup claim. Packed index owners are 86.72% smaller than F32 owners. In a different main-FP4 campaign, five 8K pairs were latency-neutral, while five 32K pairs took 1.98% more task time, with identical observed teacher logits and output IDs; profiling attributed added work to indexed batch attention. Fast presets accept this capacity/latency tradeoff, with explicit overrides. These percentages describe different cohorts and must not be added. See the [index results](../../../../speed-bench/experiments/index-five-samples-20261027/README.md) and [main 32K results](../../../../speed-bench/experiments/main-fp4-20261028/RESULTS_32K.md).

Selection itself also has distinct execution choices. DeepInfer scores inherited candidates in its index consumers and bounds scratch space by chunking. DS4 uses bounded live score rows and Metal top-k; its opt-in scalar candidate-only path skips excluded keys after layer 20 beyond 16K keys, while batch prefill still scores the dense prefix before filtering. The measured probes preserved distributions and outputs, but a small warm-decode benefit did not establish a reliable first-answer improvement. See [attention history and retrieval](../apple-silicon.md#attention-history-and-retrieval) and the [candidate experiment](../../../../speed-bench/experiments/deepinfer-alignment-20261027/README.md).

## Execution and storage on one Mac

DeepInfer's sparse-attention and MoE kernels organize computation around its supported accelerators, with distributed expert dispatch and cluster communication. DS4 uses Metal attention and groups routed work around locally available experts; unified memory and streamed weights change the bottlenecks. A smaller cache allocation creates headroom, but does not automatically enlarge a separately fixed expert-cache budget. [Routing and Metal execution](../apple-silicon.md#routing-and-metal-execution) and [streamed weights](../apple-silicon.md#unified-memory-and-streamed-weights) describe the local path.

Some dataflow lessons transfer without copying device-specific machinery: publish in the consumer's layout, bound scratch, reuse buffers and avoid unnecessary intermediate traffic. For example, DS4's packed main and index producers combine quantization with storage, although normalization and RoPE remain separate.

DeepInfer's public block manager uses GPU block references and state slots; DS4's content-addressed SSD chunks can share stored bytes, but restored graphs still own private mutable GPU arrays. SSD deduplication is not GPU paging or copy-on-write. Local checkpoint materialization is currently synchronous, even though other local expert and Engram I/O can overlap compute.

The production deployment describes disaggregated stages, network KV storage and 3FS, with some integration omitted from the release. RDMA, 3FS transport, expert replicas and cross-device migration solve cluster problems and need no direct equivalent for one Mac. See the [release boundary](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/README.md) and [local model ownership](../implementation.md#model-and-session-ownership).

Upstream asynchronous scheduling and captured graph buckets are not identical to DS4's synchronous admitted turns and Metal batching; they address different execution environments.

DS4 also supports semantic endpoints and suffix reuse for edited contexts, a local continuation facility with its own combination limits. The completed checkpoint follow-up removed extra streamed-weight sweeps: its five-pair zero-edit comparison found no clear request-time overhead and all 20 answers passed. That observation does not establish longer-session performance or erase the documented exclusions involving DSpark/MTP, steering, tensor parallelism and decoder replay. See [edited contexts](../implementation.md#edited-contexts-and-semantic-endpoints) and the [follow-up](../../../../speed-bench/experiments/context-capture-20261028/NO_EDITS.md).

## Protocol, grammar and the client boundary

The model emits DeepSeek conversation and DSML control syntax; an API client sees structured messages and tool calls. The reference recipe converts requests and responses, renders prompts and parses calls, while the inference backend generates tokens. DS4 implements its own prompt, parser and streaming projection for its supported APIs. Neither a parsed function call nor a grammar executes a tool: in DS4, the client agent owns tools, PTC and workflow state. See [conversation and tools](../reference-manual.md#conversation-tools-and-reasoning) and the [server contract](../../../SERVER.md).

Constrained decoding is another separate layer. Recipe's `OutputConstraint::ToolCalls` describes a constraint for a backend; it does not invoke DeepInfer. DeepInfer accepts caller-provided `so_args` for schema, regex or EBNF and optional trigger token IDs, then masks illegal logits, including during speculative verification. The published recipe delimiters alone do not establish an automatic mapping to those trigger IDs. DS4 constructs model-specific structural grammars around control IDs and applies constraints to drafting and target verification, with its own supported API surface. At a generation limit, typed partial calls and streamed IDs are retained without treating incomplete arguments as executable; malformed output at a normal stop remains an error. See DeepInfer's [matcher builder](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/structure_output/so_matcher_builder.py) and the local [length-finalization report](../../../../speed-bench/experiments/dsml-length-20261028/README.md).

Sampling defaults are also implementation policy, not intrinsic model constants. DS4 accepts client overrides where supported; its DS41 min-p default differs from DeepInfer's policy, and its request RNG and sampling path differ from upstream's position-keyed GPU sampling. Matching prompt and grammar therefore does not promise identical sampled text. See [sampling and speculative decoding](../reference-manual.md#sampling-and-speculative-decoding) and the [server contract](../../../SERVER.md).
