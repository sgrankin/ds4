# Kernels and weight traffic

DeepInfer and DS4 execute the same family of model operations with different hardware and weight representations. DeepInfer's public engine targets NVIDIA SM100 and Ascend 950; its NVIDIA paths call FlashMLA, DeepGEMM and related kernels. DS4's comparison here is the 1017 IQ2_XXS/Q2_K model on one Apple GPU, not a prediction from cluster throughput. The [Apple Silicon backend](../apple-silicon.md) explains its current execution and cache layouts. The public DeepInfer links below are pinned to `553741557a57df44a46fb3ab72b6aafeaf945337`; production service descriptions should not be mistaken for complete public kernel or service implementations.

## Sparse attention kernels (K1)

Sparse attention must combine the recent sliding window with selected compressed history without reading every old key. The indexer first scores eligible compressed keys and selects candidate rows; attention then reads the selected main KV rows along with the recent raw window, applies causal visibility, computes scores and a weighted value sum. DeepInfer dispatches [FlashMLA sparse prefill and KV-cache decode](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/model_executor/layers/attention_backend.py), with scheduling metadata and packed cache formats suited to its device kernels. Sparse selection and the final attention weights are different operations: a selected key can still receive little weight.

DS4 implements raw, gathered and indexed attention in [Metal and its model dispatch](../../../../src/engine/deepseek41/attention.zig), including typed F16 readers. Its index and main cache can be physically FP4 packed, while raw window rows remain expanded; consumers decode the representation they actually own. The [cache comparison](cache-and-attention.md) describes candidate inheritance and the measured packing tradeoffs. FlashMLA's CUDA SASS and tensor-memory accelerator details are hardware-specific; the transferable question is whether a Metal consumer can read the needed rows and produce the next layout with less traffic, not whether the kernel names match.

## Fuse normalization, RoPE, quantization and publication (K2)

Without fusion, a cache producer can write and reread a row between normalization, rotary position embedding (RoPE), quantization and the final store. DeepInfer's [attention producer](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/model_executor/models/v4_modules/attn.py) uses fused transforms and cache publication where supported, avoiding some intermediate materialization. Its generic transform also has a Hadamard option; V4.1's indexer does not use that transform, so importing it would change the model.

DS4's [Metal producers](../../../../src/metal/dsv41.metal) combine quantization and publication for physical main and index FP4, but normalization and RoPE remain separate and most other publication boundaries are separate. A bounded fusion would need to preserve the existing rounding points and the actual reader's representation. The qualified main path stores 288-byte rows and the index path 68-byte rows; raw SWA remains 2,048-byte F32 rows rather than the proposed 528-byte packed FP8 representation. Smaller storage alone did not guarantee speed: five 32K main-FP4 pairs cost 1.98% more whole-task time with identical observed teacher and output IDs, attributed by profiling to indexed batch-attention consumption, not standalone publication. See the [main FP4 result](../../../../speed-bench/experiments/main-fp4-20261028/RESULTS_32K.md); it applies to that workload and revision, not every context.

## Design the attention boundary for its consumer (K3)

Even when individual kernels are fast, converting layouts between a query projection, attention and the output projection adds traffic. On supported NVIDIA configurations DeepInfer can combine query normalization and RoPE, sparse attention, inverse RoPE and output quantization; the fused path returns FP8 values and scales for the next projection. It permutes Q-B and value-projection weights once to match the fused layout. The [interface](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/model_executor/layers/attention_backend.py) and [projection setup](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/model_executor/models/v4_modules/attn.py) show the contract; the fused path has platform, head-count and mode conditions, including an exclusion for dense packed-KV decoding.

DS4 stages and gathers attention data, transforms it and projects its output through more separate steps. Its F16 readers and packed consumers already specialize the boundary, but they are not the same fused pipeline. The portable lesson is to choose a producer layout for the actual downstream Metal reader and eliminate a demonstrated intermediate, while preserving numerical boundaries. The [F16 gather experiment](../../../../speed-bench/experiments/f16-gather-hour53-20261021/README.md) also records that DS4.1 does not arm the backend's deferred inverse-RoPE hook; a generic backend feature is not evidence of this model's fused execution.

## Merge independent projections sharing an input (K4)

Separate projections reading the same hidden row repeat input traffic and dispatch overhead. DeepInfer [merges compatible Q-A and raw-KV weights, and Q-B and index-Q weights](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/model_executor/models/v4_modules/attn.py), then splits the results for their respective consumers. It explicitly separates the shared-hidden KV case because that projection consumes a different hidden tensor; coincident layer placement does not make inputs identical.

DS4 generally runs these projections separately in [attention](../../../../src/engine/deepseek41/attention.zig). A same-input merge remains a candidate, not an implemented or measured speedup. Compatible weight types, numerical rounding, shared-hidden ownership and the time at which each result must be published determine which projections can safely share a call.

## Carry mHC state lazily and fuse the next boundary (K5)

Manifold-constrained hyper-connections (mHC) maintain four residual streams and use learned mixing, including Sinkhorn normalization, around each sublayer. Materializing the previous post-mix and then rereading it for the next pre-mix and normalization costs traffic. DeepInfer [carries the post-mix lazily](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/model_executor/models/v4_modules/hc.py); when its conditions hold, `mega_mhc` combines previous post, next pre, norm and cast, including output layouts for MoE. Hooks that need the trunk between post and pre prevent that fusion. Engram, steering and capture points similarly matter when considering local fusion.

DS4 has the four streams and mixing, plus fused batch RMS/projection work. PRE is the set of four mixing coefficients that weights the residual streams to form the single input row for a sublayer. At each half-layer boundary, V4.1 consumes an already supplied PRE while computing the next mixing coefficients: attention consumes the preceding FFN's PRE, and the FFN consumes the current attention half-layer's PRE. Using the newly computed PRE at that point would select a different model operation. Its narrower fusion of supplied-PRE collapse and weighted RMSNorm is **implemented**, correct in the corrected GPU fixture and neutral in five alternating full-model 8K pairs; `DS4_METAL_V41_FUSED_HC_NORM=1` remains opt-in. It uses the PRE supplied by the preceding half-layer, not the new mixer output: attention uses the previous FFN PRE and FFN uses the current attention split. It retains BF16 rounding after collapse and after weighted normalization, the existing reduction order, and stores both outputs for existing consumers. Baseline `aee06ac9`, corrected frozen revision `b3b6f079`, the initial signed-zero failure and the numerical and timing evidence are in the [HC report](../../../../speed-bench/experiments/hc-collapse-norm-20261028/README.md). This is not the upstream whole post/pre/MoE fusion or evidence of a whole-task speed gain.

## Fuse gating and resident expert work (K6)

A routed mixture of experts (MoE) selects experts, applies gate and up projections, SwiGLU, down projections and weighted combination. DeepInfer's [MLP implementation](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/model_executor/models/v4_modules/mlp.py) has fused gate and domain-local Mega MoE paths, with transformed weights and optionally shared-expert work. The latter depends on supported arithmetic and the expert-parallel group being within its NVLink domain; the public implementation and its device transport are not a generic single-GPU kernel guarantee.

DS4 already combines gate/up with SwiGLU and has summed-down, selected-address, slab and grouped paths as well as shared-expert work in [MoE](../../../../src/engine/deepseek41/moe.zig). It does not have the same whole resident Mega MoE region: host routing and SSD expert misses remain real boundaries. Its optional resident-expert substitution is an approximation that changes which logical expert executes; DeepInfer expert-parallel load balancing instead replicates the same logical expert and maps work to a physical replica. Profiling a resident local subregion is more informative than assuming a single kernel removes I/O.

The gate/up and SwiGLU result is an unpacked F16 intermediate (HALF MID); the down projection consumes those activations in a packed F16 layout (HALF PACKED). One possible smaller boundary is to write SwiGLU output directly into that consumer layout, avoiding the copy between them. In the [matched activation profile](../../../../speed-bench/experiments/packed-activation-20261028/README.md), the unchanged down pack took 39.421 ms in control and 38.129 ms in the candidate across 110 launches; this diagnostic profile is not a five-sample estimate of a future fusion's saving. The same report's five-pair full-model staged activation compression saved 105 MiB scratch but increased prefill 4.04% and whole-task time 8.07%; none of its three variants was adopted.

## Match weight packing to the GEMM consumer (K7)

Weights and scales must be laid out for the actual matrix-multiply consumer. DeepInfer [repackages its FP4, FP8 or BF16 experts](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/model_executor/models/v4_modules/mlp.py) for its supported tensor-core and Mega MoE paths. DS4's installed 1017 trunk instead uses IQ2_XXS gate/up and Q2_K down weights, although its runtime supports other formats. The [expert cache](../../../../src/engine/deepseek41/expert_cache.zig) retains those representations; Q2 bytes cannot simply be relabeled MXFP4. Repacking for a Metal consumer would need an explicit conversion, storage and numerical accounting, and the full 1017 MXFP4 artifact has not been run in this adaptation.

A separate local, user-proposed [MXS3 scale-dictionary pilot](../../../../recipes/07-native-scale-packing.md) compressed native MXFP4 scale bytes losslessly, leaving the weight codes unchanged and using raw fallback for groups with more than eight scale values. Six sampled expert matrices round-tripped exactly and saved 3.670404% including metadata with 4,096-block groups; this is a bounded storage sample, not a whole-model result. The installed routed IQ2_XXS/Q2_K formats have different scale fields, and the sampled Q2 fields exceeded the dictionary limit. There is no fused serving reader for MXS3, nor an established model-memory or speed gain. A separate Engram scale pilot saved 1.886079% on eight sampled windows, without a full-table or serving measurement. The recipe credits the user for the proposal, DeepSeek/antirez for the native data and ds4-recipe for the native layout. These are local pilots, not DeepInfer features.

A local [integer-prefill experiment](../../../../speed-bench/experiments/integer-prefill-20261027/README.md) tested a different idea without changing cached weight bytes: IQ2 gate/up values and dynamically quantized activations fed native INT8 multiplication, with Q2 down unchanged. At runtime revision `f7c93c0c3993`, five alternating three-task pairs on M5 Max increased whole-task time from 73.750 to 99.628 seconds (+35.09%) and answer prefill 34.06%; all 30 answers were correct. A favorable-only reuse variant also slowed prefill 18.49% and whole-task time 34.70% in its separate five pairs. Changed output length affects whole-task attribution, but the prefill penalty remains. Neither prototype was adopted: its runtime hooks and kernels were removed, with patches and results retained. The native integer-matmul reference was [Draw Things' kernel](https://github.com/liuliu/ccv/blob/unstable/lib/nnc/mfa/kernels/NAInt8MatMulKernel.cpp); this negative result does not prove every alternative repacking is slow.

## Fetch deterministic Engram rows early (K8)

Engram hashes compressed token n-grams to select sparse table rows, projects the retrieved embedding and gates it into the hidden state. The row addresses depend on known tokens, so fetching can start before the model reaches the consuming layer. DeepInfer's [Engram implementation](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/model_executor/models/v4_modules/engram.py) gathers sharded or host-backed tables, projects the embedding and folds constant gating weights ahead of inference. Distributed host transport is a property of that deployment, not a reason to add RDMA to one Mac.

DS4 reads selected rows from its model file with bounded SSD `pread` batches, starts deterministic prefetch early and fuses gating; [prefetch ownership](../../../../src/engine/deepseek41/engram_prefetch.zig) publishes completed rows while later batches write disjoint regions. This overlaps suitable I/O with computation but does not make SSD latency disappear, and unified memory does not remove the underlying file reads. The [backend manual](../apple-silicon.md) separates this row access from expert-weight demand loading.

## Reuse buffers and publish directly to consumers (K9)

Repeated allocation and copying of large activations can offset a kernel's arithmetic gain. DeepInfer's [mHC](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/model_executor/models/v4_modules/hc.py) and [MoE](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/model_executor/models/v4_modules/mlp.py) arrange reusable buffers and can produce activation values and scales directly in the layout of expert communication or GEMM consumers. The communication buffers and transport themselves are device- and topology-specific; preallocation and direct publication are independently useful ideas.

DS4 reuses owned scratch and batches Metal work, while its [operation boundaries](../../../../src/engine/deepseek41/ops.zig) still leave intermediate outputs for diagnostics and consumers. Its HC fusion retains both collapsed and normalized outputs rather than discarding a value still in use. A direct-write change needs to preserve ownership, lifetime, rounding and existing readers; it does not require adopting another tensor runtime. The measured activation and HC results above show why fewer writes or smaller scratch should be tested at the whole-task boundary rather than assumed to improve latency.
