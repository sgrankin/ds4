# Vision and qualification

This comparison follows DeepInfer revision `553741557a57df44a46fb3ab72b6aafeaf945337` and the current local implementation. The [DeepSeek implementation](../implementation.md#image-input-and-live-continuation) and [Apple Silicon backend](../apple-silicon.md#vision-encoder-execution) own the full local image path; this page explains the differences that matter when adapting upstream ideas or interpreting its evidence.

## Preparing arbitrary-resolution images (V1)

An image must become a patch grid and an appropriately sized sequence before language-model prefill can use it. DeepInfer expands each image placeholder according to its estimated token count and sends the image segments to CPU worker processes. The workers run the multimodal mapper asynchronously; only when the result is fetched does the scheduler mark the request schedulable. Optional shared host memory reduces transfer overhead. This allows preparation to overlap other engine work, although the worker queue and eventual image encoding still have costs. See the pinned [multimodal processor](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/ve/multimodal_processor.py) and [image processor](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/ve/processor/image_processor.py).

DS4 implements the official any-resolution geometry with native decode, resize and patch preparation, but its serving path holds inference admission across embedding-cache lookup and encoding, including preprocessing on a miss. An exact-byte cache hit avoids repeated encoding; it is not an asynchronous preprocessing pipeline. See [image resources](../../../../src/server/image_resources.zig), [image preprocessing](../../../../src/image_preprocess.zig) and [vision runtime](../../../../src/engine/vision_runtime.zig). The source establishes these control paths, not a measured latency advantage for either design.

## Encoding and batching images (V2)

DeepInfer batches raw RGB images and their variable-length metadata, then performs GPU padding and normalization into patches, the vision transformer, downsampling and the aligner. The resulting image and learned sentinel embeddings replace the corresponding language input embeddings. Its [aligner](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/model_executor/models/vision_encoder/vl_aligner.py) and [batch preparation](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/ve/prepare_tensor_input_vl.py) show the pipeline; batching and fused GPU patch preparation are distinct from the CPU worker pool.

DS4 instead prepares patches natively and executes a Metal vision sidecar per image. Its 32 transformer blocks use 1,024-wide features; the aligner groups 3-by-3 patches and projects to the 5,120-wide language representation. Workspaces hold F32 values even though weight multiplication and explicit rounding boundaries use BF16. The per-image controller and [weight binding](../../../../src/engine/vision_weights.zig) are not an equivalent batched upstream implementation; copying a multiprocessing pool is not necessary to implement a useful local optimization. A matching vision sidecar is required, as explained in the [local manual](../implementation.md#image-input-and-live-continuation).

## Image boundaries and continuation reuse (V3)

For a request such as “Describe [image],” DS4 decodes the encoded bytes, creates patches, computes projected image features and inserts the features and learned sentinels into a span of placeholder token positions. During prefill, that span supplies visual rows instead of ordinary token embeddings. The session records the image fingerprint, span start and length with its live frontier; a later continuation must match the tokens and image identity before it can reuse that state. The server's exact-byte embedding cache is a separate reuse layer: it can avoid encoding even when language state must be evaluated again. See [vision runtime](../../../../src/engine/vision_runtime.zig), [reuse](../../../../src/server/reuse.zig) and [multimodal synchronization](../../../../src/server/generation.zig).

DeepInfer strips the binary data only for images completely covered by a cached token prefix, then slices token and image metadata to the active prefill chunk and batches the remaining images. An image crossing the prefix boundary is not counted as cached; empty cached-image entries do not enter the ViT. See [cached-image handling](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/ve/multimodal_processor.py) and [chunk slicing](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/ve/prepare_tensor_input_vl.py). DS4 avoids ending its scheduling chunk inside an image span and checks fingerprints on live reuse. 

For durable reuse, explicit cache breakpoints currently support DeepSeek V4.1 text only; text-keyed disk checkpoints and state-cache persistence are gated for vision state, and suffix grafts and in-sweep checkpoint collection exclude it. Thus live image continuation and embedding reuse do not establish durable image continuation. See [persistence](../../../../src/server/persist.zig) and the [local restrictions](../implementation.md#image-input-and-live-continuation).

## Numerical and task qualification (V4)

DeepInfer's [offline examples](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/examples/README.md) compute decode perplexity from token log probabilities and compare per-sample baselines; their VL samples include single and multiple images. Its [YOCO verification](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/examples/yoco/README.md) first compares metadata for mask and compact modes, then compares log probabilities and top-k values on a fixed teacher trajectory using a compatible checkpoint. The [evaluation drivers](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/eval/README.md) cover AIME, GPQA and HLE, including image questions.

DS4 uses paired teacher-forced delta-NLL and full-vocabulary KL alongside practical task, coding, tool and protocol checks; see the [quality probe](../../../development/benchmarking.md#paired-quality-probe) and [methodology](../../../lab/methodology.md#quality-and-interpretation). Positive delta-NLL means lower likelihood of reference tokens, and its exponential is a teacher perplexity ratio, not a task failure rate. KL describes distribution drift on identical histories; partial top-token lists cannot establish full KL. Neither metric automatically rejects an approximation or substitutes for actual task outcomes. Reuse compatible fixtures where useful, but compare the same checkpoint, quantization, histories and settings: upstream hardware and native checkpoint scores are not measurements of the local 1017 IQ2_XXS/Q2_K trunk.

## Profiling and performance sweeps (V5)

DeepInfer's [benchmark and sweep documentation](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/examples/README.md) separates profiler traces from steady-state timing and plots throughput-latency curves over batch settings. Its encoder sweep times GPU padding through the aligner, excluding asynchronous CPU preprocessing and host-to-device transfer; decode throughput uses full-acceptance accounting unless adjusted for an assumed acceptance rate. Those scopes cannot be read as complete request latency. The profiler itself perturbs timings, so its traces identify costs rather than supply final throughput.

Locally, choose one outcome, fix a baseline, change one thing, measure, inspect and decide within the one-hour experiment loop. Include ordinary, favorable and adverse workloads; for tunable features plot speed and quality tradeoffs. Comparative performance claims require at least five measured samples per side, alternating order, retaining all samples and reporting variation; profile-off request or task measurements need their own defined cache and startup conditions. The [methodology](../../../lab/methodology.md) owns these conventions. Existing local tools are sufficient for targeted questions; upstream's broad framework and multi-device scores need not be imported to learn from its sweep design.

The upstream [Pareto plotting tool](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/examples/sweep/plot_pareto.py) is the specific sweep-visualization reference from the original audit. Its results remain tied to its workload and hardware.
