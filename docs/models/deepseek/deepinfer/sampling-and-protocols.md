# Sampling, constraints and protocol conversion

A model token becomes a client-visible tool call through several distinct owners. The prompt supplies tool declarations and model control tokens; a backend may constrain the next token; the sampler chooses from the permitted logits; a matcher advances with the selected token; and a protocol parser turns generated DeepSeek tool-call markup (DSML) into a named call and argument fragments. The client executes the resulting call. For example, after a tool-call opening token, a structural grammar can allow a declared function name and its parameter syntax while rejecting unrelated tokens. A sampled token advances the matcher before the next mask is made; the output parser then emits semantic name and argument updates. Neither that grammar nor the parser executes the function.

This comparison uses [DeepInfer revision 5537415](https://github.com/deepseek-ai/DeepInfer/tree/553741557a57df44a46fb3ab72b6aafeaf945337) and [deepseek-recipe revision 935817c](https://github.com/deepseek-ai/deepseek-recipe/tree/935817c66f5d6e64838f419692545f06787e485f). DS4's supported client contract is described in the [server manual](../../../SERVER.md#constrained-output-and-client-tools); the [comparison](comparison.md) places these paths in the wider model implementation.

## Reusing grammar masks during speculative decoding (S7)

A vocabulary mask describes which next token IDs are legal at one matcher state. In DeepInfer, the CPU matcher first accepts the previously committed output, fills a mask for the current state, then walks the tentative draft tokens and saves a separate mask after each accepted draft. It rolls that walk back, asynchronously copies masks and their request indices from pinned host memory to the GPU, and applies the appropriate position's mask to target logits before filtering and verification. The copy stream and event coordinate when the consumer can use the masks, allowing work to overlap. This is state-specific reuse: a mask is valid only for its corresponding prefix. See the [sampler's mask preparation and verification](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/model_executor/layers/sampler.py#L300-L457).

The DeepSeek V4.1 path in DS4 (called DS41 in the source) instead fills masks separately for the draft distribution q and target distribution p at the same prefix. It advances the tentative matcher while drafting, rewinds it, then walks only accepted target tokens and any correction; failures rewind unpublished advances. Masks precede top-k, top-p and min-p in both distributions. Flint already overlaps CPU mask preparation with the next GPU forward in packets of up to eight forwards; unsupported packet filters fall back to constrained scalar sampling. See [DS41's speculative walk](../../../../src/engine/deepseek41/speculative.zig) and the [packet qualification](../../../../speed-bench/experiments/constrained-packets-20261027/README.md). Saving DS41's masks for reuse is a later profile-driven proposal, not an established speedup.

## Compiling grammars without blocking scheduling (S8)

A compiled grammar is immutable and can be shared; a matcher holds the changing state of one generation. DeepInfer submits compilation to a worker pool and keeps a future pending until the scheduler can attach the resulting matcher. It can replay tokens when restoring matcher state. Its XGrammar compiler has a configurable cache, defaulting to 10 GiB, and can disable caching; an unbounded setting risks growth with distinct schemas. See the [builder](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/structure_output/so_matcher_builder.py) and [compiler](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/structure_output/compiler.py).

DS4 also caches compiled grammars and creates per-generation matchers, but preflight compilation is synchronous under `tool_mu`; its compiler cache is bounded at 128 MiB. An asynchronous builder could move expensive first-use compilation off that path, but the upstream cache size is not a suitable default for this machine. See [local grammar runtime](../../../../src/server/grammar_runtime.zig).

## Triggered constraints and model-specific framing (S9)

DeepInfer exposes caller-supplied `so_args` for JSON schema, regex or EBNF. Without a trigger, masking starts at the first generated token. With `trigger_token_ids`, the matcher waits for the complete sequence; an optional single `bound_token_id` forces the remaining trigger tokens after that bound is encountered. The matcher tracks partial trigger progress and restores it, the bound state and grammar state on speculative rollback. See the [builder](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/structure_output/so_matcher_builder.py) and [matcher](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/structure_output/matcher.py).

DS4 instead builds model-specific structural grammars around actual control IDs, separating reasoning from the constrained answer. Its API supports JSON objects and schemas, plus Chat regex, subject to the documented subset and combination limits; it does not expose arbitrary EBNF or DeepInfer's `so_args` interface. Strict tool schemas enforce supported argument constraints, while non-strict tools still use structural framing. See [grammar construction](../../../../src/server/grammar_format.zig) and the [server contract](../../../SERVER.md#constrained-output-and-client-tools).

Recipe's `OutputConstraint::ToolCalls` is metadata for a backend, not a call to DeepInfer. Recipe publishes V4.1 `<｜DSML｜ calls>` and V4 `<｜DSML｜tool_calls>` framing, but the inspected public code does not establish an adapter mapping these to `so_args.trigger_token_ids`. Known delimiters therefore do not establish automatic backend activation; a caller must provide the relevant backend controls. See [recipe constraints](https://github.com/deepseek-ai/deepseek-recipe/blob/935817c66f5d6e64838f419692545f06787e485f/deepseek-recipe/src/response.rs) and [DeepInfer matcher construction](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/structure_output/so_matcher_builder.py).

## Sampling location and policy (S10)

DeepInfer performs filtering, log-softmax, sampling and speculative rejection on GPU. Its optional force-top-k path works in a compact candidate space and maps selected indices back to vocabulary IDs. DS41 transfers logits to the CPU for sampling and verification; Flint has GPU sampling for supported native policies, with CPU/scalar fallback for unsupported filters. See [DeepInfer sampling](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/model_executor/layers/sampler.py) and [DS4 sampling](../../../../src/sampling.zig).

DS41's default min-p of 0.05 is an intentional local policy: it discards candidates below a fraction of the highest probability. Flint defaults to zero, and client sampling parameters can override defaults where supported. These policies and placement differences mean matching a prompt and constraint does not imply matching sampled output. GPU sampling for DS41 remains a proposal, not a measured improvement. See [request parsing](../../../../src/server/input.zig) and the [server defaults](../../../SERVER.md).

## Random draws keyed by position (S11)

DeepInfer's sampler derives random draws from a sequence seed, token position and sampling case, so a draw is independent of batch ordering for the same inputs. DS41 uses a mutable XorShift request RNG: extra speculative draws change its subsequent state. Flint's native sampler uses its own counter-based scheme. See [upstream random sampling](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/model_executor/layers/tilelang_ops/random_sampling.py) and [local sampling](../../../../src/sampling.zig).

Chat and completions parse positive request seeds; Responses currently does not. Position-keyed DS41 draws are a possible future experiment, but a seed alone cannot make different logits or sampling policies identical. See [request parsing](../../../../src/server/input.zig).

## Batch-invariant numerics and parity (S12)

DeepInfer has an opt-in NVIDIA batch-invariant mode that controls kernel and reduction choices. Its deterministic sampling also requires a fixed seed and variable-length MTP disabled. This addresses whether the same request changes when batch composition changes, not whether two different runtimes produce identical logits. See [runtime configuration](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/worker/runtime_config.py) and [engine arguments](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/engine/arg_utils.py).

DS4's scalar-versus-batch parity checks are useful tests of specific paths and fixtures, but do not establish that broader batch-invariance guarantee. Such a mode would primarily aid qualification rather than promise speed; see [local operations](../../../../src/engine/deepseek41/ops.zig).

## Rejection numerics and request failure isolation (S13)

In stochastic speculative decoding, a rejected draft is corrected by sampling the positive residual of target p minus proposal q. DeepInfer applies a small numerical bias to its rejection residual to avoid an empty distribution from rounding: with `DRAFT_PROB_PENALTY = 5e-5`, it uses `max(p - exp(-5e-5) * q, 0)` rather than subtracting q directly. The source describes the resulting bounded deviation from exact stochastic sampling. It also catches matcher failures per request in its sampling path, marking the affected request aborted instead of bringing down the whole engine. See [sampling](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/model_executor/layers/sampler.py) and the [residual policy](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/model_executor/layers/tilelang_ops/common.py) and [fused sampling implementation](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/model_executor/layers/tilelang_ops/fused_sample.py).

DS41's opt-in exact stochastic path uses FP32 positive `max(p-q)` and explicit failure and matcher rollback; packet failures invalidate affected state. These safeguards serve the same broad purpose without establishing bitwise numerical equivalence. See [local speculative verification](../../../../src/engine/deepseek41/speculative.zig) and [constraint interface](../../../../src/engine/token_constraint.zig).

## Control-token provenance and segmented encoding (S14)

A control ID inserted by the prompt renderer has different meaning from a user's ordinary text that happens to spell the same characters. Both DS4 and recipe preserve that distinction: DS4 carries prompt ranges and applies ordinary BPE to payload text, while inserting actual control IDs for framing. Recipe encodes independent segments in parallel as well as retaining their provenance. Parallel encoding is not established for DS4. See [DS41 prompt construction](../../../../src/models/deepseek41/prompt.zig) and [recipe tokenizer](https://github.com/deepseek-ai/deepseek-recipe/blob/935817c66f5d6e64838f419692545f06787e485f/deepseek-recipe-encoding/src/tokenizer.rs).

## Incremental parsing and partial calls (S15)

Recipe keeps incremental decoder and parser/matcher state as token fragments arrive, including whether marker bytes came from actual special tokens or ordinary text. It can therefore recognize framing across fragment boundaries without treating a literal spelling as a control token. DS41 and Flint stream tool names and argument fragments with stable IDs, and their final accumulated arguments preserve the streamed bytes; parts of DS4's output projection still reparse accumulated text. This is largely aligned behavior for supported cases, not a claim of full recipe feature parity. See [recipe output parser](https://github.com/deepseek-ai/deepseek-recipe/blob/935817c66f5d6e64838f419692545f06787e485f/deepseek-recipe/src/stream/output_parser.rs), [stream processor](https://github.com/deepseek-ai/deepseek-recipe/blob/935817c66f5d6e64838f419692545f06787e485f/deepseek-recipe/src/stream/processor.rs), and [local parser](../../../../src/server/ds41_output.zig).

A generation or context limit can interrupt a DSML call. DS4 retains the typed partial call, argument prefix and already-streamed ID, without canonicalizing or executing incomplete arguments or leaking raw DSML as answer text. Malformed output at a normal stop remains an error. The [length-finalization report](../../../../speed-bench/experiments/dsml-length-20261028/README.md) records the completed wire behavior. Improving incremental projection is a source-difference proposal, not evidence of a measured bottleneck.
