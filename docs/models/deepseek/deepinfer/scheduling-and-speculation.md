# Scheduling and speculative decoding

DeepInfer and DS4 both interleave prompt processing with generation and can verify several proposed tokens in one target-model pass. Their schedulers solve different resource problems: DeepInfer's public engine targets multiple accelerator ranks and paged GPU cache, while DS4 coordinates resident sessions on one Apple GPU. The production deployment described upstream includes integration not present in the public release; the mechanisms below refer to the [public engine at revision `5537415`](https://github.com/deepseek-ai/DeepInfer/tree/553741557a57df44a46fb3ab72b6aafeaf945337), unless explicitly identified as production design.

## Chunked prefill and admission (S1)

Prefill processes prompt tokens to build model state; decode extends that state to generate an answer. A long prefill can otherwise delay every active decoder. DeepInfer's [scheduler](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/csrc/engine/scheduler.hpp) admits prompt chunks under token, sequence, sequence-length and cache budgets, and avoids splitting inside an image padding region. In a distributed NORMAL engine, periodic ALL votes choose a prompt step when every rank has work; less frequent ANY votes prevent an isolated rank from starving. These votes coordinate ranks and are not needed in a one-device scheduler.

DS4's [coordinator](../../../../src/server/coordinator.zig) gives queued decode priority and admits waiting prefill slots round-robin. In batched server mode it yields after a scheduling quantum: 2,048 tokens when no generation is active, or the mixed-prefill quantum while any generation is active. The DeepSeek mixed default is 128, configurable with `--mixed-prefill-quantum`; decode requests can coalesce for 2 ms by default. For example, a long prompt arriving while another session generates receives a 128-token turn, then releases admission so waiting decode can run before its next turn. This is cooperative scheduling at turn boundaries, not interruption of an executing GPU operation. [Generation](../../../../src/server/generation.zig) preserves restored endpoints while choosing those boundaries.

The quantum is independent of engine workspace capacity: the ordinary DeepSeek engine can allocate an 8,192-row chunk, while named `ds4-local` presets explicitly select 512. A 2,048-token scheduler turn does not imply an 8,192-row engine operation, and the mixed setting applies only during active generation. The [local quantum screen](../../../../recipes/08-official-inference-lessons.md#mixed-prefill-quantum-measured-completionresponsiveness-tradeoff) illustrates the completion versus responsiveness tradeoff, but its single fixture and ordered bracket are not a five-sample comparative claim. Decoder query compaction is a separate mechanism; its current limits and proposed ordinary-chunk extension are covered in [C2](cache-and-attention.md#compacting-decoder-queries-during-prefill-c2).

## Continuous batching and pressure preemption (S2)

Continuous batching admits and retires sequences as work becomes available, instead of waiting for a fixed group to finish. DeepInfer's scheduler allocates GPU cache blocks and can preempt a running sequence under block pressure, returning ordinary requests to prefill for recomputation. Structured-output state cannot currently be recomputed this way, so such preempted requests terminate; a COMPLETION engine without a prefill channel must also stop preempted requests. See its [preemption implementation](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/csrc/engine/scheduler.hpp).

DS4 groups pending decode work in its coordinator, but DeepSeek streaming and DSpark paths may take ordered or exclusive turns rather than sharing one native GPU batch. The [batch transaction](../../../../src/engine/deepseek41/batch_transaction.zig) and [server generation path](../../../../src/server/generation.zig) define the supported cases. Evicting an idle checkpoint slot is not active-sequence block-pressure preemption; restored sessions have private mutable GPU state rather than DeepInfer's paged block ownership. More concurrent capacity would require its own allocation and admission design, not just a larger pending queue.

## Asynchronous scheduling and overlap (S3)

DeepInfer's zero-overhead scheduling (ZOS) overlaps CPU scheduling and postprocessing with device execution. Because the CPU can prepare the next step before acceptance results return, the worker repairs metadata using the actual previous result; speculative acceptance and preemption therefore matter to the pipeline. ZOS defaults on for NORMAL and COMPLETION engines and off for PROMPT, subject to configuration. See the [worker](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/worker/worker.py) and [engine arguments](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/engine/arg_utils.py).

DS4's admitted model turns are synchronous. Its coordinator permits other threads to wait and queue work, and Flint's masked packets overlap a particular CPU/GPU boundary, but neither implements the same scheduler-wide speculative metadata pipeline. CPU/GPU scheduling overlap is a possible later experiment; its value and correctness would need measurement on this backend.

## Captured graphs and decode cost curves (S4)

DeepInfer captures CUDA graphs for a set of batch-size buckets, then replays an appropriate fixed shape to reduce repeated launch and setup costs. It measures a decode cost curve for those shapes and can cache the measurements on disk; the variable-length allocator uses that curve to compare the expected output of different verification budgets. See the [graph runner](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/worker/cuda_graph_runner.py) and [performance cache](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/worker/decode_perf_cache.py).

DS4 uses Metal command batching and resident Flint packets, not this CUDA graph-bucket scheduler. The transferable objective is lower launch and idle cost, not a claim that the mechanisms or measured curves are equivalent. A local cost curve would have to measure the relevant Metal execution shapes and workload rather than reuse an NVIDIA curve.

## Block drafting and verification (S5)

Speculative decoding lets a smaller drafter propose a block, then uses the target model to check it in one pass. DeepInfer's trained multi-token prediction (MTP) path and DFlash drafter produce proposals; its [sampler](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/deepinfer/model_executor/layers/sampler.py) verifies them against target distributions. These are trained model components, not merely a scheduler predicting future tokens.

DS4's native DeepSeek DSpark path performs a real target block verification. In ordinary opportunistic mode it proposes argmax tokens and keeps the matching target-argmax prefix. Opt-in exact stochastic sampling instead samples proposal distribution `q`, accepts a token with probability `min(1, p/q)` for target distribution `p`, and on rejection samples the positive residual `max(0, p-q)`. It commits the accepted prefix and rolls back rejected state. Grammar-constrained turns mask both proposal and target distributions at each position and rewind the tentative grammar walk before verification. The [speculative cycle](../../../../src/engine/deepseek41/speculative.zig) and [constrained qualification](../../../../speed-bench/experiments/constrained-packets-20261027/README.md) describe these paths and their limits.

Drafting requires the DSpark model, sufficient target-feature history and an eligible turn; otherwise the cycle falls back to ordinary decoding. The server defaults to `--mtp-draft 1`, and native session batching does not generally enable full DSpark MTP: constrained requests can use bounded speculative turns while ordinary native batches use scalar decode. The [server configuration](../../../../src/server/boot.zig) reports these distinctions. DSP1 can preserve the drafter's raw feature history across restore, whereas DeepInfer retains projected drafter KV; its activation and five-pair restored-task evidence are explained in [the cache comparison](cache-and-attention.md#restoring-useful-drafter-history-c12).

## Confidence and verification budget allocation (S6)

A deeper proposal can save target passes when accepted but wastes verification work when rejected. DS4 limits depth and stops extending a proposal when its predicted confidence falls below the Metal default of 0.6. This is a per-request cutoff, not a cross-request allocation. `--dspark-confidence 0 --mtp-draft 6 --mtp-exact-sampling` was an eager experimental policy, not the ordinary default; the [DSP1 qualification](../../../../speed-bench/experiments/draft-features-five-20261028/README.md) separately measures five alternating pairs at 0.6 on three restored tasks, with matching observed outputs. It does not establish a general draft-allocation speedup.

DeepInfer optionally chooses a shared verification budget across scheduled requests. It multiplies successive confidence estimates to estimate each position's probability of being reached and accepted, ranks those cumulative probabilities, and compares expected accepted tokens per unit of measured graph and sampler time. Allocating the best positions resembles filling an inverse cumulative distribution or water-filling across requests: a position with higher estimated marginal return receives budget before a lower one. With ZOS, older confidence informs the total budget while newer GPU metadata can repair per-request allocation. Variable-length mode defaults off and maximum draft length defaults to five. See [allocation](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/csrc/engine/mtp_varlen.hpp) and [confidence accumulation](https://github.com/deepseek-ai/DeepInfer/blob/553741557a57df44a46fb3ab72b6aafeaf945337/csrc/engine/scheduler.hpp). A comparable local allocator remains a proposal and would require eligible concurrent drafting, a Metal cost curve and task-quality measurements.
