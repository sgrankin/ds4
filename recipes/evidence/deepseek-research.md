## Recommendation

The highest-value **new algorithm to try** is opt-in **decoder bounded replay**, initially in a direct-session long-prefill experiment: preserve exact encoder computation and all compressed/index KV, but run the decoder on only the last 128 tokens, with local-attention visibility clipped to those replayed tokens. Compare against today's exact decoder dependency suffix. This is an approximation to measure, not a new exact-cache claim.

DeepInfer explicitly documents the approximation, and keeps its reconstructed decoder SWA out of its prefix cache. It is unusually relevant to DS4's CED architecture and requires no GPU cluster. However, DS4 already skips much decoder work exactly, so DeepSeek's claim of nearly halving prefill does **not** predict a similar gain here. The current server also splits syncs into 2048-token quanta, so a direct long-prefill gain would not yet be an HTTP serving gain.

## Bounded replay: concrete implementation boundary and honest limit

Official evidence:

- [Q&A, revision-pinned](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/doc/inference_deployment_qa.md#L179-L191) says local visibility becomes `[max(replay_start,i-127), i]`; decoder recomputation is approximate and does not enter prefix storage.
- [`environ.py:188–193`](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/environ.py#L188-L193) distinguishes full-query **mask** from physically **compact** modes; both use the same narrowed visibility. Their example defaults to keep140 to cover SWA plus speculative backtracking. For a first DS4 non-speculative run, keep128 covers the local window; MTP must remain off.
- [`hugging_face/config.py:47`](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/deepinfer/hugging_face/config.py#L47) explicitly sets `yoco_swa_share_hidden=False`. Thus raw decoder KV still depends on each layer, rather than all raw KV being a direct projection of encoder output. It is genuinely approximate.
- Full compressed/index publication is preserved even when queries are compacted: `v4_modules/attn.py:537–565,769–774`; boundary HC residual/pre/post mixture state is gathered together at `v4_modules/yoco.py:79–123`. Cropping only a hidden vector is insufficient.

Minimal DS4 source seam:

1. Extend the existing wide prefill decoder-suffix branch, leaving default and short/scalar paths unchanged. Keep every encoder row and layer20's full compressed/index publication. The existing `ds41_decoder_prepare` at `ds4.c:42769` already separates full publication from local-ring warming.
2. In the candidate, layers20–39 evaluate the same final128 rows. This is **not** just changing `needed`: local raw attention must have a replay floor, and no skipped higher-layer carry row may be read. `ds41_attention_batch` assembles 127 preceding ring rows (`42130–42189`); its batch kernels must receive a shortened raw view/offset or explicit lower bound. Zero-filling unseen keys would give them attention probability and would be wrong.
3. Keep absolute positions, all compressed-key causal limits and the entire HC carrier. Let normal decode continue from the resulting approximate final rings. Mark it approximate before any canonical save/cache publication; current `ds4_session_is_approximate` is backed only by `approximate_suffix` (`65389–65390`), so a small general approximate-state marker or explicitly non-exporting private caller is necessary. Do not silently label the result exact or feed it to the exact prefix store.
4. First scope: text-only Metal, TP1, no images/MTP, one wide sync. No cache-format/storage changes and no repeated suffix-relocation integration. Do not make the server scheduling quantum larger in the same experiment.

The current exact schedule evaluates 24,150 upper-layer output rows per eligible wide sweep, plus 2,540 warm-input rows and full layer20 KV publication. Fixed128 would evaluate 2,560 upper output rows. Ignoring all other work, the output-row reduction is about 11.5% for an8192-row sweep and6.1% for16384 rows; these are arithmetic proxies, **not speed predictions**. SSD layer mapping/seed costs, compressed publication/indexing and smaller-batch inefficiency remain. Current server sync quanta2048/128 (`12865–12879,13120–13139`) normally do not reach the wide>=8192 branch. Stop at a useful native-prefill result; a server adaptation would be a subsequent experiment, not smuggled into this one.

## Recipe lessons worth checking without changing runtime defaults

- **Trust token identity, not marker spelling.** The tokenizer explicitly identifies template special-token byte ranges and BPE-encodes other regions without added vocabulary (`deepseek-recipe-encoding/src/tokenizer.rs:16–25,90–116`). The output parser similarly distinguishes decoded special IDs from plain-token spellings (`stream/output_parser.rs:74–93,365–372`). DS4's direct chat append already inserts IDs and BPE-encodes payloads (`ds4.c:39974–39978,45015` onward), so that is not new. Its rendered-chat fallback scans literal marker spellings (`44926–44948`); use the official semantics when reviewing that boundary, not assume ordinary payload text is safely interchangeable with a rendered transcript.
- **Preserve protocol semantics before optimizing shared prefixes.** V4.1 recipe joins consecutive user turns, sorts tool results into call order, keeps mid-conversation System markers, and renders earlier reasoning only when tools require it (`dsv41.rs:168–192,194–231,250–320,346–412`). DS4's hidden/native tool replay and durable history are deliberate extensions: byte equality to an official *public* rendering is not evidence that replacing a live native history is free. A few offline request/prompt examples are enough for a targeted comparison.
- **Effort is not a hard token limit.** Recipe V4.1 low/high/max render50/75/100 (`dsv41.rs:20–29`); thinking temperature resolves to1.0 and top-p to at least.95 (`request/mod.rs:34–39`, `request/options.rs:79–90`). DS4 already emits numeric effort (`ds4.c:44739–44762`) and has an independent hard reasoning-budget intervention. Do not silently replace temp0 experiments with official stochastic defaults, or describe a forced cutoff as the model's trained effort control.
- **Structured-output instructions are not enforcement.** Recipe converts/schema-validates and renders JSON constraints, while the inference backend decides whether to constrain logits. DeepInfer supplies constrained decoding separately. No need to add its full grammar infrastructure to learn whether replay helps.

## 1017 architecture check

The official [1017 model card](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash-1017) calls it a minor update with improved capability and shorter task execution/output. It links the new maintained recipe and a minimal reference runtime. Its inference README expressly describes that runtime as readable reference code, not production serving.

The visible published [1017 config](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash-1017/blob/1bae0e1/config.json) and [original config](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash/blob/517ef62/config.json) match in the architecture fields inspected:40 layers/5120 hidden,384 routed experts/6 active,128 local window, compression2 then1, KV source layers2/8/14/20, index sources2/8/14/20/24/28/32/36, Engram1/14, and DSpark3 layers/5-token block/targets37–39. No new attention architecture was established by this research. This was a browser/source field comparison, not a weight or tokenizer byte comparison; ROOT owns the actual new-quant/packing/model compatibility audit. The changed checkpoint may improve practical output length and correctness independently of any runtime optimization. Validate that separately so a faster/shorter1017 answer is not credited to a Metal patch.

## Directly relevant linked libraries

DeepInfer's `.gitmodules` pins DeepSelect, FlashMLA, DeepEP and DeepGEMM (plus Ascend variants). These are CUDA/Ascend implementations, not Metal dependencies. Of them, [DeepSelect's threshold/filter/compact algorithm](https://github.com/deepseek-ai/DeepSelect/blob/main/docs/DeepSelect-deep-dive.md#algorithm) is the most self-contained portable kernel idea: scan contiguous blocks once, retain candidates above a monotonically rising threshold, periodically compact to top-k. Random block order avoids a pathological input-order cost. Preserve deterministic tie behavior and any required position ordering; the official model's reference indexer sorts selected positions, so skipping all sorting would change its numerical contract. DS4 already has optimized exact top-k variants, and long-context indexer cost must first justify this work. SM100 PTX tricks, threadblock clusters, NVLink EP and published speedups do not carry over to Metal.
